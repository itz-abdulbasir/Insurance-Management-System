Section 01

Introduction

1.1 Purpose

This Software Requirements Specification describes the functional and non-functional requirements for the Insurance Management System (IMS) — a standalone Windows desktop application built using Python, SQLite, and CustomTkinter. The system is developed as a university project to simulate a real-world insurance workflow without involving actual financial transactions.

1.2 Scope

The IMS enables three user roles — Admin, Agent, and Customer — to interact with insurance data. Customers browse plans, purchase policies, file claims, and request surrenders. Agents manage their assigned customers and handle operational tasks. The Admin has full system control. Output: a single .exe runnable on any Windows machine with SQLite.

Admin

Full system access. Manages users, plans, assigns agents to customers, reviews all claims/surrenders, views audit logs and reports.

config.py

db/connection.py — Universal Query Abstraction

import sqlite3
from config import DB_CONFIG

def get_connection():
    """Returns a live SQLite connection."""
    return sqlite3.connect(DB_CONFIG["db_path"])

def execute_query(query, params=(), fetch=False):
    """
    Universal query executor.
    fetch=True  → returns list of dict rows  (SELECT)
    fetch=False → commits the change         (INSERT/UPDATE/DELETE)
    Returns lastrowid for INSERT operations.
    """
    conn = get_connection()
    conn.row_factory = sqlite3.Row  # For dict-like access
    cursor = conn.cursor()
    try:
        cursor.execute(query, params)
        if fetch:
            return [dict(row) for row in cursor.fetchall()]
        conn.commit()
        return cursor.lastrowid
    except sqlite3.Error as e:
        conn.rollback()
        raise e
    finally:
        cursor.close()
        conn.close()

def init_db():
    """Create database + run schema.sql at first launch."""
    conn = get_connection()
    with open("db/schema.sql") as f:
        conn.executescript(f.read())
    conn.commit()
    conn.close()

6.2 Full Schema (schema.sql)

-- ─── USERS (all roles in one table) ────────────────────────────
CREATE TABLE IF NOT EXISTS users (
    user_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    full_name     VARCHAR(100) NOT NULL,
    email         VARCHAR(100) UNIQUE NOT NULL,
    phone         VARCHAR(15),
    password_hash VARCHAR(255) NOT NULL,
    role          VARCHAR(50) NOT NULL,
    is_active     BOOLEAN DEFAULT TRUE,
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- ─── AGENTS ──────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS agents (
    agent_id   INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id    INT UNIQUE NOT NULL,
    license_no VARCHAR(50),
    region     VARCHAR(100),
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- ─── CUSTOMERS ───────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS customers (
    customer_id       INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id           INT UNIQUE NOT NULL,
    dob               DATE,
    address           TEXT,
    nominee_name      VARCHAR(100),
    nominee_relation  VARCHAR(50),
    assigned_agent_id INT,
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE,
    FOREIGN KEY (assigned_agent_id) REFERENCES agents(agent_id) ON DELETE SET NULL
);

-- ─── PLANS (master catalogue) ────────────────────────────────────
CREATE TABLE IF NOT EXISTS plans (
    plan_id           INTEGER PRIMARY KEY AUTOINCREMENT,
    plan_name         VARCHAR(100) UNIQUE NOT NULL,
    plan_type         VARCHAR(50) NOT NULL,
    description       TEXT,
    min_age           INT DEFAULT 18,
    max_age           INT DEFAULT 60,
    premium_frequency VARCHAR(50) NOT NULL,
    base_premium      DECIMAL(10, 2) NOT NULL,
    coverage_amount   DECIMAL(12, 2) NOT NULL,
    policy_term_years INT NOT NULL,
    is_active         BOOLEAN DEFAULT TRUE,
    is_deleted        INTEGER DEFAULT 0
);

-- ─── POLICIES ────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS policies (
    policy_id   INTEGER PRIMARY KEY AUTOINCREMENT,
    customer_id INT NOT NULL,
    plan_id     INT NOT NULL,
    agent_id    INT,
    start_date  DATE NOT NULL,
    end_date    DATE,
    status      VARCHAR(50) DEFAULT 'active',
    created_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE CASCADE,
    FOREIGN KEY (plan_id)     REFERENCES plans(plan_id),
    FOREIGN KEY (agent_id)    REFERENCES agents(agent_id) ON DELETE SET NULL
);

-- ─── PREMIUMS ────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS premiums (
    premium_id INTEGER PRIMARY KEY AUTOINCREMENT,
    policy_id  INT NOT NULL,
    amount     DECIMAL(10, 2) NOT NULL,
    due_date   DATE NOT NULL,
    paid_date  DATE,
    status     VARCHAR(50) DEFAULT 'due',
    FOREIGN KEY (policy_id) REFERENCES policies(policy_id) ON DELETE CASCADE
);

-- ─── CLAIMS ──────────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS claims (
    claim_id         INTEGER PRIMARY KEY AUTOINCREMENT,
    policy_id        INT NOT NULL,
    filed_by         INT NOT NULL,
    reason           TEXT,
    amount_requested DECIMAL(12, 2),
    status           VARCHAR(50) DEFAULT 'pending',
    filed_at         TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    resolved_at      TIMESTAMP NULL,
    resolved_by      INT,
    FOREIGN KEY (policy_id)   REFERENCES policies(policy_id) ON DELETE CASCADE,
    FOREIGN KEY (filed_by)    REFERENCES users(user_id),
    FOREIGN KEY (resolved_by) REFERENCES users(user_id)
);

-- ─── SURRENDERS ──────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS surrenders (
    surrender_id    INTEGER PRIMARY KEY AUTOINCREMENT,
    policy_id       INT NOT NULL,
    requested_by    INT NOT NULL,
    reason          TEXT,
    surrender_value DECIMAL(12, 2),
    status          VARCHAR(50) DEFAULT 'pending',
    requested_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (policy_id)    REFERENCES policies(policy_id) ON DELETE CASCADE,
    FOREIGN KEY (requested_by) REFERENCES users(user_id)
);

-- ─── AGENT REQUESTS (assignment requests) ────────────────────────
CREATE TABLE IF NOT EXISTS agent_requests (
    request_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    agent_id    INT NOT NULL,
    customer_id INT NOT NULL,
    status      VARCHAR(50) DEFAULT 'pending',
    requested_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (agent_id) REFERENCES agents(agent_id) ON DELETE CASCADE,
    FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE CASCADE
);

-- ─── NOTIFICATIONS ───────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS notifications (
    notif_id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id  INT NOT NULL,
    message  TEXT NOT NULL,
    is_read  BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- ─── AUDIT LOG ───────────────────────────────────────────────────
CREATE TABLE IF NOT EXISTS audit_log (
    log_id    INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id   INT,
    action    VARCHAR(255),
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE SET NULL
);

6.3 Key Queries

-- Login check
SELECT * FROM users WHERE email = ? AND role = ?;

-- Customer: all own policies with plan name
SELECT p.policy_id, pl.plan_name, p.start_date, p.end_date, p.status
FROM policies p JOIN plans pl ON p.plan_id = pl.plan_id
WHERE p.customer_id = ?;

-- Agent: pending claims for assigned customers
SELECT c.claim_id, u.full_name, c.reason, c.amount_requested, c.filed_at
FROM claims c
JOIN policies p   ON c.policy_id = p.policy_id
JOIN customers cu ON p.customer_id = cu.customer_id
JOIN users u      ON cu.user_id = u.user_id
WHERE cu.assigned_agent_id = ? AND c.status = 'pending';

-- Mark overdue premiums (run on startup)
UPDATE premiums SET status = 'overdue'
WHERE due_date < DATE('now') AND status = 'due';

-- Surrender value = 60% of total premiums paid
SELECT SUM(amount) * 0.60 AS surrender_value
FROM premiums
WHERE policy_id = ? AND status = 'paid';

3.2.1 Functional Requirements

R.1: User Registration & Authentication

ID Feature Description
R.1.1 Customer Registration Self-service form: full name, email, phone, DOB (age validation), address, nominee details, and bcrypt-hashed password.
R.1.2 Staff Registration Agent and Admin registration via dedicated form; requires specific Passkey (Agent Passkey / Admin Passkey) for validation.
R.1.3 User Login & Role Routing Login with email, password, and role selection (Customer/Agent/Admin). Success redirects to role-specific dashboard; failure shows inline red error.
R.1.4 Account Approval Newly registered Agents and Admins remain inactive until manually approved by an existing Administrator via the Pending Approvals hub.

R.2: Master Insurance Plan Management

ID Feature Description
R.2.1 Create Insurance Plan Admin feature to add new plans with name, type (term, endowment, etc.), base premium, coverage amount, term years, and age limits.
R.2.2 Deactivate / Delete Plan Admin can deactivate (is_active=0) or soft-delete (is_deleted=1) plans. Deletion triggers the Decommissioning Workflow for active policies.

R.3: Policy Purchase & Schedule Generation

ID Feature Description
R.3.1 Browse & Select Plan Customers view active plans via interactive cards with a detailed "View Benefits" page for each insurance type.
R.3.2 Purchase Policy Customer selects plan → confirms start date → system validates age eligibility → creates policy record.
R.3.3 Automated Premium Scheduling On purchase, system automatically generates the entire premium schedule (Weekly, Monthly, etc.) in the premiums table.

R.4: Premium Payment & Ledger Management

ID Feature Description
R.4.1 Overdue Premium Sweep Startup task: Automatically flags premiums as 'overdue' if due_date < current date and status is 'due'.
R.4.2 Process Premium Payment Customers mark own premiums as 'paid'; Agents can mark paid on behalf of assigned customers. Updates paid_date and audit log.

R.5: Claims and Surrender Workflows

ID Feature Description
R.5.1 File an Insurance Claim Customers file claims against active policies. Requires reason and requested amount. Status set to 'pending'.
R.5.2 Request Policy Surrender Customers request early exit. System calculates simulated Surrender Value (60% of paid premiums).
R.5.3 Adjudicate Requests Agents/Admins review pending claims and surrenders in their dashboards to Approve or Reject with remarks.
R.5.4 Plan Decommissioning Refund If an Admin deletes a plan, all associated active policies are 'terminated'. Customers receive a notification to file a full refund claim.

R.6: Reporting and PDF Generation

ID Feature Description
R.6.1 Generate Premium Receipt Customer/Agent can download a detailed PDF receipt for paid premiums, including full policy lifecycle data and payment history.
R.6.2 Generate Policy Summary Admin and Agent can export table-based PDF reports for user lists, policy summaries, and claim histories.

R.7: System Auditing

ID Feature Description
R.7.1 Immutable Audit Logging Every critical system action (login, pay, claim, delete) is recorded in audit_log with User ID, Action, and Timestamp.

Section 11

Feature Workflows — How Things Work

11.1 Login & Registration Flow

FLOW
User opens app → LoginWindow
    ├─ Enter email, password, select role from dropdown
    ├─ Click "Login"
    │     ├─ DB: SELECT * FROM users WHERE email=? AND role=?
    │     ├─ Row found → bcrypt.checkpw(input, stored_hash)
    │     │     ├─ Match    → "Login Successful!" → close window
    │     │     │              → open AdminWindow / AgentWindow / CustomerWindow
    │     │     └─ No match → show "Invalid credentials" (red inline label)
    │     └─ No row → same error
    │
    └─ Click "New User? Register"
          ├─ Open RegisterWindow
          ├─ Fill form → Click "Register"
          │     ├─ Validate: email format, phone 10 digits, age from DOB
          │     ├─ hash = bcrypt.hashpw(password, bcrypt.gensalt())
          │     ├─ INSERT INTO users → get user_id (lastrowid)
          │     ├─ INSERT INTO customers/agents with user_id
          │     └─ "Registered! Please login." → back to LoginWindow
          └─ "Back" → return to Login

11.2 Policy Purchase Flow

FLOW
Customer → "Insurance Plans" tab
    ├─ App loads: SELECT * FROM plans WHERE is_active=1
    ├─ Plan cards displayed per type
    ├─ Customer clicks "Choose Plan"
    │     ├─ Dialog: confirm start date, preview premium schedule
    │     ├─ Click "Confirm Purchase"
    │     │     ├─ INSERT INTO policies (customer_id, plan_id, agent_id, start_date, status='active')
    │     │     ├─ Calculate end_date = start_date + policy_term_years years
    │     │     ├─ Generate premium schedule:
    │     │     │     delta = {weekly:7, monthly:30, quarterly:90, yearly:365} days
    │     │     │     for i in range(total_installments):
    │     │     │         due = start_date + timedelta(days = i * delta)
    │     │     │         INSERT INTO premiums (policy_id, amount, due_date, status='due')
    │     │     ├─ Log to audit_log
    │     │     └─ Show "Policy Created! ID: XXXX"
    │     └─ Cancel → back to plans

11.3 Claims Flow

FLOW
Customer → "File a Claim" tab
    ├─ Dropdown: all ACTIVE policies of this customer
    ├─ Enter reason (text area) + amount_requested
    ├─ Click "Submit Claim"
    │     ├─ Validate: policy status must be 'active'
    │     ├─ INSERT INTO claims (..., status='pending')
    │     ├─ Log to audit_log
    │     └─ "Claim submitted. ID: XXXX"

Agent → "Claims Management" tab
    ├─ SELECT pending claims WHERE assigned_agent_id = this agent
    ├─ Click claim row → see full details
    ├─ Click "Approve" or "Reject" + enter remark
    │     ├─ UPDATE claims SET status=?, resolved_by=?, resolved_at=NOW()
    │     ├─ If Approved → UPDATE policies SET status='claimed'
    │     └─ Log to audit_log

Customer → sees updated status in "My Claims" tab

11.4 Surrender Flow

FLOW
Customer → "Surrender Policy" tab
    ├─ Dropdown: all ACTIVE policies
    ├─ App computes: surrender_value = SUM(paid premiums) × 0.60
    ├─ Shows: "Surrender Value: ₹XX,XXX (simulated)"
    ├─ Enter reason → "Request Surrender"
    │     ├─ Validate: policy status = 'active'
    │     ├─ INSERT INTO surrenders (..., status='pending')
    │     └─ Log to audit_log

Agent → "Surrender Management" tab
    ├─ View pending requests from assigned customers
    ├─ "Approve" or "Reject"
    │     ├─ UPDATE surrenders SET status=?
    │     ├─ If Approved → UPDATE policies SET status='surrendered'
    │     └─ Log to audit_log

11.5 Premium Payment Flow

FLOW
On app startup (main.py):
    UPDATE premiums SET status='overdue'
    WHERE due_date < DATE('now') AND status='due'

Customer → "Premium Payments" tab
    ├─ SELECT premiums WHERE policy_id IN (customer's policies) AND status != 'paid'
    ├─ Table: due_date | amount | status badge
    │     due    → orange badge
    │     overdue → red badge
    ├─ Click "Mark as Paid"
    │     ├─ UPDATE premiums SET status='paid', paid_date=CURDATE()
    │     └─ Log to audit_log
    └─ Row badge turns green ✅

from db.connection import init_db

13. Implementation Updates

The following features and architectural changes have been successfully implemented as of the latest update:

  • Database Migration: The backend was successfully migrated from a MySQL server to a lightweight, local SQLite database, removing the need for a separate database server while preserving all schema relationships and cascading behaviors.
  • Standalone Packaging: The entire application, including the SQLite database engine, CustomTkinter assets, and Python runtime, was packaged into a compiled standalone executable (IMS.exe) using PyInstaller for seamless deployment.
  • Agent/Admin Passkey Security: Registration for Agents and Admins is now secured with a dedicated passkey requirement (e.g., AGENT_PASSKEY, ADMIN_PASSKEY), preventing unauthorized staff account creation.
  • Admin Approval Workflow: All newly registered Agents and Admins are inserted into the database with an is_active=0 (pending) state. They cannot log in until an existing Admin navigates to the newly implemented Pending Approvals tab on the Admin Dashboard and formally approves their account.
  • Multi-Agent Concurrency: Leveraged SQLite's concurrent connection handling to ensure a robust multi-agent system, allowing multiple agents to log into separate application instances and manage customers simultaneously.
